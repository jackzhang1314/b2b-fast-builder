# B2B Fast Builder

### 用 AI，把客户的搜索需求变成你的外贸网站。

为外贸公司、工厂和 SEO 团队准备的 AI 建站 Skill。适合快速构建产品独立站、小语种站和细分市场站，持续覆盖与真实业务相关的长尾搜索需求。

**搜索数据规划页面 · 每个网址完整 HTML · 询盘先保存再发邮件 · 用 AI 持续更新**

> 网站不是你想展示什么就做什么，而是客户在谷歌搜什么、数据指向什么，就优先做什么。

[核心价值](#ai-leverage) · [快速开始](#quick-start) · [适合谁](#who) · [AI 站群与长尾 SEO](#multi-site) · [看懂架构](#architecture) · [建站流程](#workflow) · [常见问题](#faq)

## 它是什么？

你可以把 Skill 理解成一份交给 AI 的“建站工作手册”：不仅告诉 AI 怎么做页面，还约定如何规划产品分类、收集真实资料、检查搜索引擎能否读到内容，以及让询盘真正送达。

把它导入有代码、文件和执行能力的 AI Agent，例如支持相应能力的 Codex、Claude Code 或其他工具，再用日常语言描述业务。Agent 按流程帮你规划、编写、检查和部署，你负责确认产品事实、设计效果与必要授权。

**本仓库提供工作规范、配置示例和验证脚本，不是下载后直接运行的成品网站，也不是自带账号的在线建站平台。** 实际网站由 Agent 根据你的资料构建，完成哪些功能以项目实现和测试为准。

<a id="ai-leverage"></a>

## 核心价值：用 AI，让你的产品覆盖更多市场的采购需求

你已经有产品、参数、应用经验和交付能力，却不一定有足够的人手，为每个市场重新写内容、做网站、维护页面。**这正是这套 Skill 适合发挥 AI 价值的地方：把真实产品资料，变成不同市场的客户能搜索、能看懂、能询价的页面。**

“精准获客”不是吸引所有人来看，而是让正在找某种产品、规格或解决方案的采购商，有机会从 Google 自然搜索找到你。自然搜索不按点击收广告费，但调研、内容、建站和维护仍有成本。

### AI 放大的，是整套建站与更新能力

1. **把产品知识变成采购内容。** Agent 根据已核实的产品资料和搜索需求，协助整理分类、参数、选型说明和采购问答，而不是只批量写泛泛的文章。
2. **把一个市场的工作经验复用到更多市场。** 复用组件与生成流程，按当地搜索用语、计量单位和真实服务范围调整内容，减少每增加一种语言都从头建站的工作。
3. **让小团队也能逐步运营多个产品站或语言站。** 内容由 AI 协助修改，页面提前生成完整 HTML，再检查和发布；无需每个站都维护一套内容管理后台。

我们的建议是：先验证一个品类或市场，再扩展有效的方法。**AI 降低的是内容制作与网站维护的重复成本，不是替你省掉市场判断和事实核对。**

### 国家域名的本地定位优势，也是值得采用这套方案的理由

例如，`.de` 面向德国、`.pl` 面向波兰，能向 Google 和用户传递明确的目标国家信号。Google 官方说明，地域定向可能改善目标国家的排名，但也可能牺牲其他地区的表现。这支持的是**本地定位与相关性优势**，不是买到国家域名就自动获得高排名。见 [Google 地域定向说明](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites#geotargeting)。

因此，如果你确实服务某个国家，可以考虑用符合注册条件的国家域名，配合当地语言、产品选型和交付信息，建立面向这个市场的网站。国家和语言并不一一对应，域名选择应跟着真实市场走。

### 小语种的机会，来自尚未被充分回答的采购问题

先看当地客户实际搜什么，再看现有结果是否缺少清楚的参数、选型、适配或采购说明。**如果需求存在、现有内容又回答得不好，才是值得用 AI 协助补足的机会。** 不能仅凭“这是小语种”，就认定竞争低或需求大。

把这套方法记成一句话：**找到当地需求，用 AI 做好对应页面，再用真实访问和询盘验证。** 它适合产品长尾、小语种本地化和有业务区分的多站运营，不依赖无限增加网站数量。

## 适合谁，适合做什么？

| 你的情况 | 可以用它做什么 |
|---|---|
| 工厂或工贸一体企业，准备做第一个独立站 | 围绕产品、采购需求和真实企业资料，建立询盘型网站 |
| 外贸公司，经常研究新产品或新市场 | 先研究搜索需求，再为有业务基础的品类搭建产品站 |
| 想覆盖法语、西班牙语等市场 | 制作有独立网址、完整译文和本地采购信息的语言版本 |
| SEO 团队，需要运营多个网站 | 复用页面组件、内容结构和检查流程，减少重复搭建工作 |
| 已有主站，准备做某个细分产品或用途专题 | 根据需求决定新增分类页、专题页，还是独立网站 |

它尤其适合：**不需要内容管理后台，愿意让 AI 修改资料并重新发布的网站。**

如果团队需要每天登录后台上架产品、多人审核、草稿发布、角色权限或实时编辑，应选择带 CMS 的完整版 `b2b-builder`。极速版的取舍是减少后台系统，不是减少真实内容和上线检查。

<a id="multi-site"></a>

## 为什么适合 AI 站群与长尾 SEO？

### 先找客户的具体需求，再决定做哪些页面

“长尾词”可以理解为客户更具体的找货方式。例如，同样是找挖掘机，有人关心吨位，有人关心动力，有人需要某种工况下的设备。

以下仅是页面规划示例，不代表这些词已经完成搜索量或竞争验证：

| 客户可能搜索什么 | 页面应该帮他解决什么 |
|---|---|
| `2 ton mini excavator` | 比较 2 吨机型的参数、尺寸、用途和采购选项 |
| `electric mini excavator` | 了解电动机型的续航、充电、工况与限制 |
| `excavator buckets for sale` | 查找铲斗类型、适配机型、规格与报价入口 |

这不是一个关键词就生成一张网页。同一需求的不同说法可以由一个页面回答；有明显不同的选型任务，才值得增加分类或专题。

Skill 指导 Agent 使用产品词、修饰词、搜索量、搜索意图和行业对标来规划页面。**没有搜索数据，就先列“待验证的方向”，不会把 AI 的猜测包装成调研结论。**

### 复用建站方法，不重复造网站系统

如果你要经营多个品类、品牌或市场，可以复用同一套组件、样式规则、页面生成方式和上线检查；各站分别维护自己的产品、采购信息、语言与询盘配置。

这套架构对多站运营的价值主要有四点：

1. **少维护一套后台。** 无需为每个站再搭建 CMS、运营账号和后台插件体系；产品内容由 Agent 改文件、检查后重新发布。
2. **新增页面有统一规则。** 同类产品共用页面模板，参数、导航、网址和搜索标题从内容数据生成，减少逐页复制时的遗漏。
3. **每个站可以独立更新与回退。** 当前规范按站点分别构建和验证，不把多个域名混在一次单站检查里。
4. **同一品牌的图片可以共享。** 需要多站共用素材时选 R2；普通单站则让图片随网站发布，少配一个服务。

**当前提供的是可重复执行的多站建站规范，不是“一键管理几百个网站”的站群控制台。** 跨站批量发布、统一任务调度和数据总看板需要另行实现。

### 一个站能解决的事，不一定要拆成十个域名

同一品牌、同一产品体系，往往可以先用一个网站的分类页和语言目录承接需求。有不同品牌定位、产品体系或真实市场运营需要时，再评估独立站。

独立站可以分开管理项目、部署和市场测试，**但不意味着把 AI 内容分到多个域名，就能免于 Google 的处理。** Google 明确把“用多个网站掩盖规模化内容”的做法列为违规示例。这里的“AI 站群”指有实际业务价值的多站运营，不指换个域名、换个国家名就复制低价值页面。见 [Google 搜索垃圾内容政策](https://developers.google.com/search/docs/essentials/spam-policies#scaled-content)。

AI 可以帮助研究主题和组织内容，关键是准确、相关、对客户有帮助；问题不在于是否用了 AI，而在于是否规模化生产缺少用户价值的内容。见 [Google 生成式 AI 内容指南](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)。

建站效率可以复用，客户价值不能省略。更多页面不会自动带来更多排名或询盘。

<a id="architecture"></a>

## 不懂技术，也能看懂的架构

你只需要区分两件事：**展示产品的页面提前做好；客户提交询盘时，再调用专门的接收服务。**

```text
公司资料 + 产品数据 + 页面组件
              │
        AI 修改、构建与检查
              │
      每个网址生成完整 HTML
              │
     Cloudflare Pages 托管网站
              │
         客户浏览、提交询盘
              │
    Pages Function 校验提交内容
              │
        D1 先保存询盘记录
              │
       Resend 向你的邮箱发通知
              │
      进入感谢页，记录一次转化
```

### 1. 静态 HTML：把页面提前准备好

可以把它想成：客户打开网页时，直接拿到已经排好的产品说明，而不是先等浏览器执行程序，再拼出主要内容。

每个重要网址都有自己的 HTML 文件，例如：

```text
/                         → 首页
/mini-excavators/         → 小型挖掘机分类页
/2-ton-mini-excavator/    → 2 吨产品页
/contact/                → 联系与询盘页
```

标题、产品说明、参数和内部链接都在最初返回的 HTML 中。Google 能处理 JavaScript，但预生成让主要内容的读取少依赖浏览器脚本，Google 官方也认可预渲染的价值。**这提供可抓取的技术基础，不等于保证收录或排名。** 见 [Google JavaScript SEO 指南](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。

### 2. React：用同一套零件组装页面

React 在这里主要负责复用产品卡、分类页、参数表等组件；Vite 负责打包，构建程序把每个网址写成完整 HTML。默认不需要 Next.js 或常驻的页面渲染服务器。

对于你来说，实际好处是：增加一批产品时，可以沿用已经确认的布局；调整公共样式时，不必逐页手工修改。菜单、表单等交互仍可使用必要的 JavaScript，静态不等于不能点击、不能询盘。

### 3. 无 CMS：把更新工作交给 Agent

“没有 CMS”就是没有一个专门让你登录、上产品的内容管理后台。更新方式是给 Agent 发资料或指令：

> 把这三款产品加到小型挖掘机分类，使用我上传的参数表和图片。先给我预览，确认后再发布。

Agent 修改项目中的内容文件，重新生成页面并执行检查。你不用手写代码，但更新需要一次构建和部署，不是后台保存后立即生效。也因此，团队高频协作编辑更适合 CMS 版本。

### 4. D1 + Resend：邮箱是通知入口，不是唯一存档

客户提交后，先保存到 D1，再发邮件。只要保存成功，即使邮件通知暂时失败，记录仍可查询，并按项目实现补发；保存失败则不能假装提交成功。

成功提交后进入独立感谢页，便于配置 Google Ads 等转化追踪，并通过询盘编号防止刷新重复计数。**收到邮件、查到记录、感谢页跳转都要实际测试。** 本版不自带询盘管理后台，备份通过 D1 控制台或项目实现的查询工具查看。

### 5. 自己保留项目，减少服务商绑定

网站代码、内容与配置保存在你自己的项目中，生产账号和域名由你控制。不是只有某一家建站服务商能替你改一段文字。

静态前端可以迁移到其他兼容托管平台；D1、邮件、域名和其他集成迁移时仍需相应适配，不能理解为整个系统搬到哪里都零改动。第三方依赖和素材仍遵守各自许可。

## 实际使用：先看到网站，再一步步上线

### 第一步：说清楚你卖什么、客户是谁

提供主要产品、目标市场和参考网站即可开始。已有关键词表、行业调研或公司资料可以直接交给 Agent；暂时没整理完，也能先规划样板。

### 第二步：先看三个样板页

优先做首页、一个产品分类页和一个产品详情页。你可以直接说“这块太花”“产品图片放大”“这里要加参数表”，有批注能力的工具也可以圈选修改。

默认采用专业 B2B 企业风格：产品摄影、清晰分类、克制配色、有秩序的留白和采购信息。产品区不拿 SVG 机器插画、通用图标或空洞卡片充数。

### 第三步：确认样式，换成你的真实资料

Agent 会主动邀请你上传公司介绍、产品照片、图册和参数表，负责整理、匹配产品并替换内容，再扩展其余页面。

前期可以用可使用的摄影素材或明确标记的 AI 示意图帮助确认设计。正式发布前，必须核对真实型号、参数和图片使用权。**样式确认，不等于内容确认。**

### 第四步：需要哪个服务，再接通哪个

- 准备部署或线上测试时，才引导连接 Cloudflare。
- 准备把询盘发到邮箱时，才引导连接 Resend。
- 你选择在线聊天且开始安装时，才引导连接 Tidio。
- 只有选择 R2 并真正需要上传时，才配置图片存储。

不在开场让你注册一长串账号。Agent 在当前环境允许、任务已授权时主动补齐必要工具，每轮只告诉你现在要做什么。账号登录、付费确认和必要授权仍由你完成；密码、验证码、私有 API Key 不发送到普通聊天。

### 第五步：验证后发布，之后继续用 AI 更新

正式发布前检查页面、手机端、图片、链接和询盘。上线后再发一条测试询盘，确认数据库记录、邮箱收件、感谢页和所选聊天都正常。

后续可以让 Agent 换图、改文案、补产品、增加语言页面。它需要修改原始内容、检查受影响页面并重新部署，而不是直接改一份无法复现的线上文件。

<a id="languages-media"></a>

## 小语种与图片，怎么选择？

### 小语种：翻译好的页面，也要有自己的网址

可按项目规划使用语言目录、子域名或独立域名。比如采用英语主站时：

```text
example.com/products/       英语
example.com/fr/products/    法语
example.com/ja/products/    日语
```

每种语言先准备并核对译文，再生成完整 HTML；不是客户点一下翻译按钮，才临时把页面变成另一种语言。产品术语、单位、询盘文案和服务范围也要检查。

Skill 要求独立网址与正确的语言对应标记（hreflang），但不附带现成的一键全站翻译引擎，翻译、路由和检查由 Agent 在项目中实现。Google 同样建议不同语言采用不同 URL。见 [Google 多语言网站指南](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)。

### 图片：先简单，需要共享再独立存储

| 方案 | 白话解释 | 更适合 |
|---|---|---|
| 默认 local | 图片和网页一起打包发布 | 单站、常规产品图，希望少配置服务 |
| 可选 R2 | 图片放在独立素材库，页面引用图片地址 | 同一品牌多个网站共用图片，或有较大文件 |

用 R2 不会把页面变成动态页面，也不需要因此搭一个 CMS。不同客户的素材需要隔离；图片共享是工程便利，不是 SEO 加分保证。

## 快速开始

### 1. 导入完整 Skill

如果你的 Agent 支持 GitHub 子目录导入，使用：

```text
https://github.com/jackzhang1314/b2b-fast-builder/tree/main/skills/b2b-fast-builder
```

如果工具只接受仓库链接、能自动扫描 `skills/` 目录，使用：

```text
https://github.com/jackzhang1314/b2b-fast-builder
```

手动安装时，将整个 [`skills/b2b-fast-builder`](skills/b2b-fast-builder/) 文件夹放入所用 Agent 的技能目录。不要只复制 `SKILL.md`，它还需要同目录中的参考文档、示例配置和验证脚本。

导入方式以各工具实际能力为准。仅能聊天、不能操作项目文件或执行代码的工具，无法独立完成这里的构建与部署。

### 2. 把这段话发给 Agent

```text
使用 b2b-fast-builder，帮我构建一个无 CMS 的外贸 B2B 网站。

我销售：[产品]
主要客户：[进口商 / 经销商 / 工厂采购等]
目标市场与语言：[市场和语言]
参考网站或现有资料：[链接 / 附件，暂无也可以]

先帮我规划产品分类和核心页面，再做首页、分类页、详情页三个样板。
设计要专业、大气，适合真实的 B2B 企业。
样式确认后，提醒我上传自己的公司资料和产品素材。
不要一开始就让我注册云服务，到需要部署或接通邮件时再引导。
每个重要网址必须预生成完整 HTML，询盘先保存，再发到我的邮箱。
```

使用支持 `$技能名` 的工具时，可写 `$b2b-fast-builder`。看到样板后先反馈，再继续全站；不需要一开始就写一份技术需求书。

## 不只做出页面，还要检查什么？

以下是 Skill 要求 Agent 在项目中落实的交付标准，不是本仓库已经替你的新站完成的测试：

- **能直接读取**：每个重要网址有完整 HTML，主要内容不依赖浏览器执行 JavaScript。
- **页面关系正确**：标题、规范网址、导航和站点地图相互一致，未知网址正确返回 404。
- **内容可信**：使用客户真实资料，不编造认证、产能、客户案例或询盘成绩。
- **手机端可用**：产品图、参数表、菜单和表单在手机上也能正常操作。
- **询盘有记录**：先保存后通知，失败有提示和查询路径，成功进入感谢页。
- **更新有检查**：类型检查、代码检查、已有测试、页面构建和静态输出验证，通过后才能部署。

仓库已提供静态输出和 Tidio 安装代码的验证脚本；审美、翻译质量、素材真实性和真实收件仍需实际复核。PageSpeed 四项 100 只能依据对应页面、设备和时间的实测报告展示，不保证所有页面永久满分。

## 常见问题

### 建站和自然流量都是免费的吗？

不是。自然搜索访问通常不按广告点击付费，但 AI 工具、域名、资料制作、托管、邮件以及维护仍可能产生成本。这个方案减少了 CMS 和常驻页面渲染服务的负担，不等于零成本。

多站规划也要检查托管项目数、构建次数、文件数量/大小、数据库和邮件额度，不能承诺无限建站。各服务以当前套餐为准，部署约束见 [Cloudflare Pages 限制](https://developers.cloudflare.com/pages/platform/limits/)。

### 做好网站，就能获得精准询盘吗？

不能保证。这里的“精准获客”是规划目标：用合适的页面回答潜在采购者的需求，并把联系入口接好。实际结果还取决于需求、竞争、产品、内容、信任、搜索排名和持续运营。

### 只能用某一种 AI 吗？

不把规范绑定到某一家模型。能读取 Skill、操作代码和执行必要工具的 Agent 才能按流程完成项目；不同平台的浏览器、终端、授权和安全输入能力会影响自动化程度。

定时更新可以在支持调度的工具中另行配置，但本仓库不自带常驻 Agent、跨站调度器或自动经营系统。

### 没有 CMS，是不是完全没有数据库？

不是。**产品内容放在项目文件里，客户询盘保存在 D1。** 没有的是产品内容管理后台，不是取消询盘存档；在线聊天记录则在你自己的 Tidio 收件箱中，默认不会同步到 D1。

### 当前用 Pages，还是 Workers？

本版实施规范仍采用 **Cloudflare Pages + Pages Functions**。截至 2026-09-04，Cloudflare 官方已优先推荐新项目采用 Workers；本仓库尚未提供对应迁移流程，不把两者描述成已经可以直接互换。这里介绍的是当前版本架构，选型时请核对 [Cloudflare 官方说明](https://developers.cloudflare.com/pages/)。

### 技术组成

| 部分 | 当前选择 | 作用 |

node skills/b2b-fast-builder/scripts/test-validate-static-output.mjs
node skills/b2b-fast-builder/scripts/test-validate-tidio-output.mjs
